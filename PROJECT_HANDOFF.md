# Anfisa VPN Handoff

## Что это

`Anfisa VPN` — отдельное desktop-приложение для Windows, которое:

1. тянет публичные прокси-конфиги из репозитория `kort0881/vpn-vless-configs-russia`;
2. собирает их в одну локальную базу;
3. отбрасывает мусор и дубликаты;
4. делает быструю сетевую проверку;
5. делает real-check через `HiddifyCli`, то есть проверяет, проходит ли реальный трафик через прокси;
6. сохраняет только рабочие результаты;
7. показывает их в красивом UI и даёт кнопку открытия в `Hiddify`.

Файл:

Что делает:

- дедуплицирует по `exit_ip`;
- умеет фильтровать по странам до real-check;
- умеет исключать страны;
- умеет ограничивать объём real-check для ускорения;
- учитывает пользовательский blacklist;
- сохраняет JSON результата в:
  `C:\Users\rysla\AnfisaVPN\data\results\latest.json`

## Как сейчас работает открытие в Hiddify

Найден и проверен рабочий deep-link импорт через официальный URL Scheme Hiddify.

Документация:

- https://github.com/hiddify/hiddify-app/wiki/URL-Scheme

Проверено локально:

- `hiddify://import/<proxy_link>`

Через PowerShell `Start-Process` профиль реально добавляется в `Hiddify`.

Важно:

- старый вариант `install-proxy?url=...` оказался ненадёжным;
- рабочий вариант для приложения сейчас: `hiddify://import/<config_with_pretty_Anfisa_label>`

Важно:

- сам deep-link импорт реально добавляет профиль;
- но `Hiddify` для single-proxy часто всё равно сбрасывает tag до `trojan § 0`;
- поэтому в приложении добавлен пост-патч свежесозданного JSON-профиля в папке `Hiddify`.

## Текущие проблемы / хвосты

### 1. Godot MCP bootstrap

Иногда при запуске нового проекта через MCP появляется ошибка про:

`res://mcp_interaction_server.gd`

Это не логика приложения, а каприз runtime/bootstrap.
Для пользователя приложения это не критично, но для удобной отладки через MCP это стоит дочистить.

### 2. Регион не всегда читается из тега

Сейчас регион берётся:

- сначала из текста/кода в теге;
- если там пусто или мусор, то подставляется реальная `exit_country`.

Это уже сильно лучше, но можно сделать ещё умнее:

- полноценный разбор emoji-флагов;
- улучшенный парсинг кодов стран;
- нормализацию по базе.

### 3. Visual polish / UX

Скелет уже приятный, но до “коммерческого” вида ещё нужно:

- фирменная графика;
- кошка `Anfisa`;
- более сильные карточки и акценты;
- анимации и микровзаимодействия;
- красивые loading/state transitions;
- иконка приложения.
- интерфейс всё ещё выглядит слишком сыровато;
- нужно лучше разнести блоки по вертикали и сделать layout очевиднее;
- по отзыву пользователя текущая визуальная оценка низкая.

### 4. Автоматизация / качество выдачи

Сейчас уже всё ключевое внутри программы:

- запуск проверки;
- обновление результатов;
- просмотр рабочих конфигов;
- открытие/копирование в `Hiddify`.

Но ещё можно докрутить:

- автообновление по таймеру;
- фильтры по протоколу/региону в UI;
- сортировку по latency / exit country / protocol;
- кнопку “только уникальные выходы”;
- экспорт в файл / историю прогонов.
- кнопку `Mark bad / Blacklist`, чтобы пользователь одним кликом выкидывал плохой прокси из следующих прогонов.

Фактически `Blacklist` уже начат:

- backend читает `user_blacklist.json`;
- UI пишет плохие конфиги в blacklist;
- нужно ещё окончательно отполировать UX этой части.

### 5. Проверка против поведения самого Hiddify

Важный найденный момент:

- часть конфигов проходила наш ранний real-check, но не работала в `Hiddify`;
- причина оказалась в расхождении формата `ws`-транспорта;
- real-check синхронизирован ближе к импортируемому профилю `Hiddify`;
- после этого и пользовательского blacklist выдача стала меньше, но честнее.

### 6. Почему в выдаче в основном Trojan

Сейчас не потому, что другие протоколы специально скрываются, а потому что:

- `Trojan` чаще переживает real-check на текущем пуле;
- `VLESS` и `VMess` в текущих источниках почти не доживают до рабочего результата;
- в pipeline они всё ещё участвуют, но редко доходят до финального списка.
